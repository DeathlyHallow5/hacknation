## Стенд

- **160 живых хостов** в случайных местах диапазона (seed 2026): 120 × nginx 1.27, 20 × httpd 2.4, 20 × redis 7.
  Остальные 16 222 адреса — пустые.

- Машина: ноутбук разработчика, Docker Desktop (WSL2); контейнер `core` без ограничений CPU.

## Что тормозило

На партию из 1024 адресов до исправления:

| Этап | Время |
|---|---:|
| pre-flight `nmap -sn -PS<15 портов>` | **~100–160 с**, 100 % CPU |
| naabu, 8 портов | ~4 с |
| `nmap -sV` + httpx | ~15 с |

Без root-прав nmap пингует хосты через `connect()`. На мёртвые адреса соединения висят до таймаута,
а с повторами (по умолчанию) они копятся, и nmap крутит цикл опроса на одном ядре.
Замер на одной /22 (6 живых хостов — во всех вариантах найдены все 6):

| Флаги pre-flight | Время |
|---|---:|
| как было | 158 с |
| `-T4` | 103 с |
| `--max-retries 1` | 174 с |
| `-T4 --max-retries 1` | 107 с |
| `--min-hostgroup 1024 --min-parallelism 512 --max-retries 0` | 9 с |
| **`-T4 --max-retries 0`** (выбрано) | **6 с** |

`--max-retries 0` безопасен, потому что pre-flight ничего не отсекает: naabu всё равно проверяет
каждый адрес (с повтором), а pre-flight только *добавляет* живые хосты без открытых портов из списка.
Потерянный пакет означает максимум один такой «молчащий» хост, но не потерянный сервис.

## Рассмотренные альтернативы

| Вариант | Вывод |
|---|---|
| **RustScan** вместо naabu | Тоже только находит порты, сервисы определяет через nmap. naabu у нас не узкое место (~4 с на 1024 адреса). У RustScan нет точного лимита пакетов/с — только число одновременных соединений, а лимит темпа — требование AGH. Вывод — построчный JSON у naabu, который мы уже разбираем и который принимает DefectDojo. |
| **`-sS`** / naabu SYN (`compose.syn.yaml`, выключен по умолчанию) | Быстрее `connect()` и не оставляет записей в логах приложений, но нужен raw-сокет: root или `CAP_NET_RAW`. Сейчас `core` работает без root и с `cap_drop: ALL`. Сделано опционально: `naabu-raw` с `cap_net_raw`, включается `compose.syn.yaml`. Первый замер (с помехой) **потерял открытый порт у 17 из 66 хостов**, у CONNECT — 0 из 160. Пока не включать; повторить на свободной машине. |
| **`-p-`** (все 65 535 портов) | В 8 192 раза больше проб, чем 8 портов. /18 при 1000 pps: 16 382 × 65 535 / 1000 ≈ 1,07 млн с ≈ **12 суток**. Для обзора сети — top-100/1000; `-p-` — точечно на конкретном хосте. |
| **`-T5`** | Таймаут ответа 300 мс, меньше повторов: в реальной сети теряются медленные хосты, а темп не ограничивается — против требования безопасного сканирования. У нас темп задаёт `--max-rate` из профиля. |
| **`-Pn`** | У naabu уже стоит (каждый адрес проверяется). У nmap `-sV` тоже. В сочетании с `-p-` на пустых адресах — максимум лишних проб. |

## Оговорки

- Это локальная L2-сеть Docker: RTT меньше миллисекунды, мёртвый адрес отвечает быстро (ARP).
  В маршрутизируемой сети пакеты к мёртвым адресам просто пропадают — время упирается в таймауты и лимит pps.
- Нижняя граница от лимита: 16 382 адреса × (8 портов naabu + 15 проб pre-flight) / 1000 pps ≈ 6,3 мин.
  Мы получили 7,9 мин, то есть лимит pps почти полностью использован; ускорение дальше — только
  поднятием лимита (решение администратора сети, не сканера).
- Top-100 портов не замерялся. По той же оценке для /18 при 1000 pps: 16 382 × 115 / 1000 ≈ 31 мин;
  при лимите 5000 pps — около 6–8 мин.
- Сканер нашёл сам себя (`10.77.63.254`) — см. [NOISE.md](NOISE.md), «Что осталось».
