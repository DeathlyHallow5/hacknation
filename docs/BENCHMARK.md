# Бенчмарк: сеть /18 (16 382 адреса)

> 2026-11-21. Один прогон через `/api/v1/scans`, как из дашборда. Скрипты:
> [`scripts/bench/bench_setup.py`](../scripts/bench/bench_setup.py) поднимает стенд,
> [`scripts/bench/bench_run.py`](../scripts/bench/bench_run.py) запускает скан и сверяет результат с планом.

## Стенд

- Docker-сеть `10.77.0.0/18` (`internal`, без выхода наружу) — **16 382 адреса**.
- **160 живых хостов** в случайных местах диапазона (seed 2026): 120 × nginx 1.27, 20 × httpd 2.4, 20 × redis 7.
  Остальные 16 222 адреса — пустые.
- Сканер (`core`) подключён к той же сети, его адрес `10.77.63.254` в диапазон входит.
- Профиль: 8 портов `22,80,443,3306,5432,6379,8080,8443`, лимит **1000 пакетов/с**, партии до 1024 адресов (/22).
- Машина: ноутбук разработчика, Docker Desktop (WSL2); контейнер `core` без ограничений CPU.

## Что тормозило

На партию из 1024 адресов до исправления:

| Этап | Время |
|---|---:|
| pre-flight `nmap -sn -PS<15 портов>` | **~100–160 с**, 100 % CPU |
| naabu, 8 портов | ~4 с |
| `nmap -sV` + httpx | ~15 с |

Без root-прав nmap пингует хосты через `connect()`. На мёртвые адреса соединения висят до таймаута,
а с повторами (по умолчанию) они копятся, и nmap крутит цикл опроса на одном ядре.
Замер на одной /22 (6 живых хостов — во всех вариантах найдены все 6):

| Флаги pre-flight | Время |
|---|---:|
| как было | 158 с |
| `-T4` | 103 с |
| `--max-retries 1` | 174 с |
| `-T4 --max-retries 1` | 107 с |
| `--min-hostgroup 1024 --min-parallelism 512 --max-retries 0` | 9 с |
| **`-T4 --max-retries 0`** (выбрано) | **6 с** |

`--max-retries 0` безопасен, потому что pre-flight ничего не отсекает: naabu всё равно проверяет
каждый адрес (с повтором), а pre-flight только *добавляет* живые хосты без открытых портов из списка.
Потерянный пакет означает максимум один такой «молчащий» хост, но не потерянный сервис.

## Оценка времени скана

Мастер «Nowe skanowanie» показывает оценку до запуска (`POST /api/v1/scans/estimate`). Первая версия была
взята из демо-данных панели и сильно занижала: для лабы /24 обещала 49 с при фактических 280 с. Модель с
2026-11-22: каждый адрес получает пробы pre-flight и пробы naabu (`-Pn`) по всем портам профиля под общим
лимитом запросов/с, плюс ~6 с на подгруппу (`-sV`, httpx) и ~20 с на прогон (старт, сравнение, сигнатуры).
Сначала pre-flight слал 15 фиксированных проб; со scope-политикой он проверяет порты профиля, и модель
считает 2 × порты на адрес. Замеры ниже сделаны ещё с 15 пробами pre-flight.

| Прогон | Профиль | Факт | Было в оценке | Стало |
|---|---|---:|---:|---:|
| лаба /28 (14 адресов) | Szybki: top-100, 100 запросов/с | 42 с | — | 42 с |
| лаба /24 (254 адреса), запуск из панели | Szybki | 280 с | 49 с | 318 с |

### Лимит и без лимита: что на самом деле ограничивает скорость

Оба прогона — 2026-11-22, коммит `a42db80`, один и тот же стенд (/18, 160 живых хостов, 8 портов), DefectDojo
остановлен. Снятие лимита (1000 → 100 000 запросов/с) ускорило скан всего на **5 %** (420 → 397 с).
Если бы время уходило на сами пробы под лимитом (16 382 адреса × 2 × 8 портов / 1000 ≈ 4,4 мин), без
лимита они заняли бы секунды и скан стал бы вдвое быстрее. Этого не произошло: скорость упирается не в
лимит, а в ожидание — соединения к пустым адресам ждут отказа или таймаута при ограниченном числе
одновременных соединений (naabu `-c 100`), а живые хосты проходят `nmap -sV` и httpx. Разбивку по этапам
в этих двух прогонах не замеряли. Вывод для эксплуатации: лимит 1000 запросов/с почти ничего не стоит по
времени и сильно снижает нагрузку на сеть — поэтому он по умолчанию. В штатном режиме потолок системы —
10 000 запросов/с (проверка в настройках и в схеме БД); для прогона «без лимита» она снималась временно.

## Рассмотренные альтернативы

| Вариант | Вывод |
|---|---|
| **RustScan** вместо naabu | Тоже только находит порты, сервисы определяет через nmap. naabu у нас не узкое место (~4 с на 1024 адреса). У RustScan нет точного лимита пакетов/с — только число одновременных соединений, а лимит темпа — требование AGH. Вывод — построчный JSON у naabu, который мы уже разбираем и который принимает DefectDojo. |
| **`-sS`** / naabu SYN (`compose.syn.yaml`, выключен по умолчанию) | Быстрее `connect()` и не оставляет записей в логах приложений, но нужен raw-сокет: root или `CAP_NET_RAW`. Сейчас `core` работает без root и с `cap_drop: ALL`. Сделано опционально: `naabu-raw` с `cap_net_raw`, включается `compose.syn.yaml`. Первый замер (с помехой) **потерял открытый порт у 17 из 66 хостов**, у CONNECT — 0 из 160. Пока не включать; повторить на свободной машине. |
| **`-p-`** (все 65 535 портов) | В 8 192 раза больше проб, чем 8 портов. /18 при 1000 pps: 16 382 × 65 535 / 1000 ≈ 1,07 млн с ≈ **12 суток**. Для обзора сети — top-100/1000; `-p-` — точечно на конкретном хосте. |
| **`-T5`** | Таймаут ответа 300 мс, меньше повторов: в реальной сети теряются медленные хосты, а темп не ограничивается — против требования безопасного сканирования. У нас темп задаёт `--max-rate` из профиля. |
| **`-Pn`** | У naabu уже стоит (каждый адрес проверяется). У nmap `-sV` тоже. В сочетании с `-p-` на пустых адресах — максимум лишних проб. |

## Оговорки

- Это локальная L2-сеть Docker: RTT меньше миллисекунды, мёртвый адрес отвечает быстро (ARP).
  В маршрутизируемой сети пакеты к мёртвым адресам просто пропадают — время упирается в таймауты и лимит pps.
- Нижняя граница от лимита: 16 382 адреса × (8 портов naabu + 15 проб pre-flight) / 1000 pps ≈ 6,3 мин.
  Мы получили 7,9 мин, то есть лимит pps почти полностью использован; ускорение дальше — только
  поднятием лимита (решение администратора сети, не сканера).
- Top-100 портов не замерялся. По той же оценке для /18 при 1000 pps: 16 382 × 115 / 1000 ≈ 31 мин;
  при лимите 5000 pps — около 6–8 мин.
- Сканер нашёл сам себя (`10.77.63.254`) — см. [NOISE.md](NOISE.md), «Что осталось».

## Как повторить

Сеть бенчмарка должна быть разрешена политикой: в `.env` добавьте
`ASI_ALLOWED_CIDRS=172.30.0.0/24,10.77.0.0/18` и поднимите стек с доступом к API
(`docker compose -f compose.yaml -f compose.api.yaml --profile lab up -d`). Порты профиля бенчмарка — из
`ASI_ALLOWED_PORTS` по умолчанию.

```bash
python scripts/bench/bench_setup.py up bench_plan.json   # сеть asi-bench + 160 контейнеров + core в сети
BENCH_NOTE="что поменяли" python scripts/bench/bench_run.py .env bench_plan.json p8 "22,80,443,3306,5432,6379,8080,8443" 1000 22
# результат допишется в docs/benchmarks/history.csv
python scripts/bench/bench_setup.py down
```
