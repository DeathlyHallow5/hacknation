# Deployment and recovery

Use compose.production.yaml as a standalone Compose project. This configuration runs the API in inventory-only mode (ASI_MAX_RUNS=0). Only the TLS proxy publishes a port. The core and database have internal networks. Provide release images by repository and SHA-256 digest, an operator-controlled public hostname, and a matching certificate and private key. Mount secrets from files outside the checkout. The database URL must contain the same password as the database secret, URL-encoded when necessary. Validate with docker compose -f compose.production.yaml config --quiet. The built images must include the current security changes.

For a local lab worker, approve explicit IPv4 CIDRs and numeric ports with ASI_ALLOWED_CIDRS and ASI_ALLOWED_PORTS. ASI_EXCLUDED_CIDRS overrides approvals. Profiles using top-port presets require conversion to explicit approved ports. ASI_GLOBAL_PPS is shared across configured worker slots within one instance; this is a scanner argument ceiling (nmap --max-rate, naabu -rate, httpx -rl), not packet-level enforcement. A packet-level limit cannot be enforced from inside the core container: it runs with cap_drop ALL and without NET_ADMIN, so it cannot install tc/nftables policers on its own interface. Enforce one outside, at the worker's network boundary (host tc/nftables on the bridge or uplink, or a firewall in front of the scanned network), when a hard ceiling is required. Domain targets are resolved once per batch by the core and every address checked against ASI_ALLOWED_CIDRS; the scanners receive only those addresses (httpx connects to the pinned address and sends the approved name as Host and TLS SNI), so a name re-pointed after the check (DNS rebinding) cannot lead a tool elsewhere. httpx never follows redirects (the profile setting follow_redirects is not passed to it); a Location header is stored as data and never fetched. Addresses reported by the tools outside the batch fail the batch. Create deploy/control/STOP on the host to interrupt running scanner processes and refuse further launches. Keep it present until an administrator clears the incident. If an immediate network cutoff is required, isolate the worker at the network boundary.

## Client addresses behind the proxies

The login limiter (5 failures per login, 20 per address in 15 minutes), sessions and the audit log use the client address. The core takes X-Forwarded-For into account only when the TCP peer is listed in ASI_TRUSTED_PROXIES (compose.yaml: the dashboard's fixed address 10.231.70.250; compose.production.yaml: 10.231.71.250), and then uses the right-most entry that is not itself a trusted proxy; any other peer is the client, whatever headers it sends. The dashboard image preloads frontend/client-ip.mjs, which replaces X-Forwarded-For with the address taken from the socket, or, when the socket peer is one of the dashboard's own ASI_TRUSTED_PROXIES (production: the TLS proxy, 10.231.72.250), with the right-most untrusted entry of the proxy's header. Caddy sets X-Forwarded-For to the TCP peer and discards the client's. The fixed subnets 10.231.70.0/24 to 10.231.72.0/24 must not collide with other networks on the host. If the dashboard is put behind another proxy, add that proxy's address to the web service's ASI_TRUSTED_PROXIES (ASI_WEB_TRUSTED_PROXIES in compose.yaml), never to the core's.

## Backup and key rotation

1. Pause workers, stop writes, record the application image digest, migration version and current key version. Create a PostgreSQL custom-format dump and encrypt the backup at the storage layer. Keep the matching versioned ASI_DATA_KEY in separate restricted storage.
2. Restore into an isolated empty database. Verify migration versions, row counts and decryption of representative evidence without displaying plaintext. Exercise login and viewer redaction.
3. Rotate first on that restored copy, then on the deployment, with the built-in rotation (core/src/keyring.rs covers every pgcrypto column; a unit test fails when a migration adds one it does not know):
   1. Generate a new key (openssl rand -base64 32). Set it as ASI_DATA_KEY and move the old key to ASI_DATA_KEY_PREVIOUS (or ASI_DATA_KEY_PREVIOUS_FILE, a secret mounted next to data_key in compose.production.yaml). Restart all instances together.
   2. Reads now fall back to the previous key, so the dashboard keeps working. Administracja → Ustawienia → Szyfrowanie shows both key identifiers and the number of rows still under the previous key (counted at startup).
   3. Press "Wykonaj rotację klucza" (POST /api/v1/security/encryption/rotate, permission settings:manage). Rows under the previous key are re-encrypted in batches of 200, each locked and rewritten in its own transaction; rows already under the new key are skipped, so the rotation can be repeated or resumed after a failure. The request and its result (counts, key identifiers, never keys) are recorded in the audit log. Rows that neither key decrypts are counted and left untouched: they need an older key.
   4. When the status shows 0 rows under the previous key, remove ASI_DATA_KEY_PREVIOUS and restart. Keep the old key with the backups that need it (step 5).
   Keys are bound parameters or per-connection session settings, never stored; still avoid SQL parameter logging (log_statement=all, auto_explain with parameters) during the rotation.
4. On failure the rotation can simply be run again. If the database must be restored, restore the snapshot and the key version it was taken with together.
5. Enforce backup expiry and preserve older keys until the last backup requiring them expires. Historical backups and old database rows may contain credentials collected before the redaction change. Rotate exposed credentials independently.

## Outstanding acceptance evidence

A production release with active scanning still requires packet-level egress tests (DNS pinning and redirect handling are implemented, see above, but not yet verified at packet level) for approved domains, DNS rebinding, redirects, exclusions and overlapping runs; per-subnet token budgets and observation of emergency stop latency. Validate the deployed TLS endpoint, backup restoration and data-key rotation with the operator's release images and certificate. Review access to shared records versus user-owned objects and verify that legacy evidence, user-entered notes, titles, redirects, imported data, backups and exports comply with the deployment's retention policy.
